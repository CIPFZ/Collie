## 4. Collie 本身的问题

1. **「head_sha 必须是本轮 task 提交的后代」这条检查和 attempt 机制冲突**（`src/run.ts:1168`）。
   - 中断之后，代码可能在上一轮就已经全部提交了，本轮只需要补写 report。这时正确的 head_sha 就是上一轮的最后一个代码提交，它一定早于本轮的 task 提交。
   - 这条检查会对每一次「只补 report」的续跑都判 BLOCK，`--continue` 模式下的返工也会这样。
   - 这条检查本来是用来防 worker 乱填 head_sha 的。在 attempt 机制下，应该改成「head_sha 是**首次** `base_sha` 的后代」（和 v02-e-fix 让取证沿用首次 base_sha 一致），再加上「head_sha 在 HEAD 之前」。
2. **沿用首次 base_sha 时，取证范围会把 R1 在两次运行之间的提交也包进来。**
   - `556049e..HEAD` 里有 R1 的 `357e110`，它改了 `.collie/collie.toml`、`AGENT-worker.md`、`SPEC.md`、`docs/backlog.md`，合计 5 个受保护文件，+62/−3 行。
   - 这一轮因为 head_sha 停在 `09f229c`，`556049e..09f229c` 里的受保护改动是 0 行，没出事。但只要 attempt 2 的 worker 在 `357e110` 之后提交了新代码，取证范围就会覆盖 R1 的改动，规则 2 会误判 BLOCK。
   - 上报路径写 progress 时就已经把 R1 的提交列进了「提交」一栏，这就是这个问题的表现。
   - 根本原因是：在同一批次的两次运行之间，R1 往 main 上推了受保护文件的改动。规格里还没有「R1 在两次 attempt 之间不得改受保护路径」或者「取证要排除 R1 的提交」这样的规定。
3. **续接会话很贵。** 只干了 15 轮、输出 3,903 token 的活，花了 $21.49，比第 1 次干 130 轮完整活的 $18.13 还多。续接时上一次的整个会话要重新写入缓存。像「只补 report」这种续跑，开一个新会话、靠 task.md 的中断说明和 git log 接手，可能更便宜，v02-e-drill 那次新开会话只花了 $1.85。
4. **reviewer 的白名单还是没能实测。** 这已经是连续两轮因为上报路径没拉起 reviewer。
